# Rider workflow, phone layout and offer notifications — 13 November 2026

Local implementation only. No backend deployment, push or installable signed APK release was performed.

## Rider workflow

- Rider acceptance begins automatic location tracking toward pickup. Acceptance still reserves a job: it does not claim physical possession of a parcel.
- One collection confirmation starts an intrastate delivery. New clients request `autoStart:true`; carrier and last-mile acceptance also records the accepted handoff and journey-start events in one transaction. Existing clients retain compatible manual checkpoint APIs.
- Older collected jobs resume their journey automatically when the updated rider app opens. Final delivery still requires the customer's OTP.
- No app GPS start/stop buttons, separate journey-start button or manual delivery-sync button. Network reconnection and periodic sync are automatic. Missing permissions and failed connections remain visible, without simulated positions or repeated success toasts.
- A genuine authenticated fix sent to `/api/v3/rider/location` is applied only to that rider's active, assigned handling legs. It covers multiple parcels with one device location source, excludes strangers and old handlers, and requires a current observation timestamp.
- Android uses its foreground location service and visible notification; its heartbeat checks for remaining active deliveries, stopping when none remain or the session is revoked. A PIN screen lock does not itself revoke an active native delivery session. Explicit logout/account changes stop tracking. Browser GPS needs the page active/open.
- The OS retains control over location permissions, location services, foreground service restrictions and battery behaviour. Tracking cannot be guaranteed if a rider disables these or force-stops the app. No location is inferred from shipment status.
- The live map can display the accepted rider heading to pickup while custody still belongs to the vendor. The public/vendor status remains accurate.
- Nearby offers funded by a wallet hold are actionable, as are paid checkout offers; unpaid offers remain blocked.

## Phone system bars and responsive layout

- Native Android now applies system-bar, cutout and keyboard insets to a FrameLayout containing the WebView. Resizing the actual web viewport keeps CSS-fixed bottom navigation inside the usable phone area.
- Insets handling covers supported Android versions, with API guards and legacy keyboard resize handling. Native-applied insets are consumed and identified to web CSS to prevent double padding.
- Browser views use safe-area CSS variables on all four sides. Bottom navigation is centred within the safe horizontal region, including asymmetric landscape cutouts.
- Greeting text can wrap without overlapping search/notification buttons. Native text zoom follows the phone's font-size setting.

## Offer notification behaviour

Every eligible rider gets their own durable inbox event, including two riders eligible for the same shipment. Eligibility includes location/service area, vehicle/load compatibility, identity status, account availability/capacity and any explicit rider assignment. Wrong-area, suspended or otherwise ineligible riders are excluded.

Only the first successful acceptance claims an open shipment. Concurrent competing requests return one success and one conflict; the shipment then disappears from other riders' available offers.

New shipment/funding events now kick the FCM queue instead of relying solely on its 15-second fallback sweep. The wake runs outside the request's database context so it cannot reuse an already released PostgreSQL client. The durable retry/sweep remains as recovery.

This is prompt best-effort delivery, not a guaranteed instant alert. FCM needs the matching Firebase Android build, a registered installation token, current rider session, notification permission, correctly activated server credentials and connectivity. OS/provider delivery can be delayed. Separate rider accounts on separate phones can both receive alerts. On one phone, switching saved accounts does not make logged-out accounts receive the active account's notifications.

## Route-and-direction eligibility update

Open offer notifications and acceptance now require an explicitly selected active configured route and direction. Riders choose these in **Nearby deliveries → Routes I’m available for**, then mark themselves available. This is declared operating availability, not a claim that GPS reveals an intended destination.

- An opposite-direction or different-destination selection does not match.
- Existing pickup city/state/community, vehicle, load, identity and capacity checks still apply.
- No selected route, paused availability, an inactive route or a stale selection after route revision prevents new open offers. Old unconfigured shipments are not broadcast to the open marketplace. Existing private dispatch workflows remain compatible.
- The API derives rider ownership from the session, validates route revisions, and only permits reverse selection for bidirectional routes. Route preferences are durable and included in SQLite-to-PostgreSQL migration.
- Nearby offers refresh automatically without replacing unsaved route form selections.
- Push delivery checks current eligibility again immediately before sending; a claimed shipment or no-longer-matching rider makes the queued offer obsolete.
- First-to-accept is enforced server-side, including across API instances. Opening an app alone does not reserve a shipment.
